### Important

**I1. The Task 5 race tests depend on wall-clock timing and can flake on a loaded machine.** Plan:4591-4678 (with `quick()` at Plan:4256-4261).

- **What's wrong:** Both tests assume a 250 ms timeout fires inside a 500 ms sleep, and that a spawned task is polled within 50 ms.
- **Failure windows** (on `#[tokio::test]`'s default current-thread runtime, where cargo runs test threads in parallel and the Nx gate also runs core-rust):
  - `a_timeout_that_queued_first…`: if the test thread is not polled for about 240 ms after the approval is created, the waiter times out before `pending_approvals` ever sees it pending. The test then panics after 5 s ("1 approvals never became pending").
  - `a_decision_that_queued_first…`: a stall of about 240 ms before the spawned decision reaches the mutex lets the timeout queue first. The test then unwraps a 409.
- **Ruling:** rewrite both tests without timers.
  - Use `patient()` timeouts.
  - Hold `control_plane_transaction()`. Spawn the exact timeout path, `coordinator.settle_approval(&id, Settlement::TimedOut)`, then `tokio::task::yield_now().await`. On current-thread, the spawned task registers on the fair mutex before the test resumes. Then spawn `decide_approval`, `yield_now()`, and drop the guard. Do the reverse order for the other test.
  - Mark both `#[tokio::test(flavor = "current_thread")]` explicitly.
  - Keep `a_timeout_denies_the_call_and_a_late_decision_conflicts` (with `quick()`, no race) as the coverage for the timer branch.
  - Do not add tokio `test-util` or paused time (Cargo.toml:36; paused time would also fire the 5 s helper timeouts).

**I2. Escalating from a broad exec rule to self-approval is neither documented nor warned about.** Plan:11566, Plan:7027 (README text), Plan:593-617 (suggestions), Plan:9711-9721 (card scope line).

- **What's wrong:** Local owner auth trusts any loopback request that carries an allowed `Origin` (routes/http.rs:114-150). With "Always allow `curl`", or a prefix for any interpreter, package runner, or git, the model can POST `/api/agents/{id}/approval-policy` (`exec: allow`) or `/approval-rules` with a forged Origin. That turns one narrow rule into unrestricted shell, and it persists.
- **Second vector:** writes are allowed by default, so `.git/config` (`core.fsmonitor`) or `package.json` scripts make "Always allow `git status`/`npm test`" arbitrary code (no `.git` guard at HEAD).
- **Suggestions make it easy:** `suggested_matcher` offers one-word prefixes such as `curl` or `python3` for a single click.
- **Why the alternatives don't help:**
  - A per-approval token or a web-only header can be fetched through the same forgeable owner-read routes.
  - Tool markers can't be detected: curl sets its own headers, and the env is already cleared.
  - On the VPS the internal API key already blocks a bare curl.
- **Ruling (proportionate, within spec §1/§14):**
  1. Add a "Limits" paragraph to the README Approvals section (Task 7): a rule for an HTTP client, interpreter, shell, package runner, or git lets the companion act as the owner on this machine, including changing its approval policy, because writes are allowed by default.
  2. In `ApprovalCard` and the Approvals page Add-rule form, show a one-line warning when an exec-class matcher is `any`, or when its first word is on a short list (`curl wget python* node bun deno ruby perl php sh bash zsh env sudo xargs npx bunx npm pnpm yarn make git cargo go docker ssh`).
  3. No token or nonce. Nothing in spec §14 requires one.

**I3. The behavior change for unattended and non-web sources is under-documented, and the risk note is wrong about the legacy route.** Plan:38, Plan:11567, Plan:7027.

- **What's wrong:** With default `exec: ask`, a bash call from any non-web source waits for a web decision:
  - A check-in blocks its own automation (single-flight) for 30 min.
  - A job blocks the agent's job lane for 30 min, then carries on denied.
  - A Telegram chat is held for 15 min, and Telegram gets no hint that anything is waiting.
  - The CLI's legacy `/run` returns **408 at 10 min** from the daemon's own `run_request_timeout` (app.rs:98, routes/mod.rs:712-736). The approval keeps waiting, so a later Allow in the web runs the command with nobody watching.
- **Spec intent:** spec §7.3 applies the timeouts uniformly and singles out only Telegram, so waiting is intended. There is no job-specific timeout, and adding one would be a spec deviation.
- **Ruling:**
  - Keep the behavior.
  - Add README copy (Task 7 Approvals section): check-ins, jobs, Telegram, and CLI/API runs also wait for a web decision. The legacy `/run` answers 408 after `ANIMAOS_RS_RUN_REQUEST_TIMEOUT` (600 s) while the approval still waits. To run unattended shell work, set that agent's `exec` to `allow` or add a rule.
  - Correct the Plan:11567 risk note.
  - Record "Telegram/CLI notice that an approval is waiting" as a post-M4 follow-up (not approval from Telegram, which is a non-goal).

**I4. The M4 rollback path is not documented.** Plan:37, Plan:11568.

- **What's wrong:** The v7 bump means an M3 binary refuses the file. Rolling back needs `.pre-approvals.bak`, or `control_plane.backup.6` in Postgres. M2 and M3 each added this bullet to the daemon README in the same milestone (README.md:358-359). The plan defers it to M10, and no task schedules it.
- **Ruling:**
  - Task 2 (or Task 7) adds a bullet modelled on README.md:359: "Rolling back from M4 to an M3 daemon…", naming both backups. It says control-plane changes since the upgrade are lost (policies, rules, sessions, runs), that the history store stays in place, and that M3 ignores its `approvals` rows.
  - Keep the v7 bump itself (see §7c).

**I5. Task 8's warning check runs two extra `cargo check` builds on a disk-tight machine.** Plan:8141-8142.

- **What's wrong:** `cargo check -p anima-daemon` and `cargo check --tests` produce check-profile `.rmeta` artifacts for the whole dependency graph (fastembed/ort, sqlx, reqwest…), separate from the test build. This is likely about 1 GB or more with about 13 GB free while the Nx gate needs about 12 GB (carry-forwards "Repo facts"). It can starve Task 14's gate.
- **Also:** "expected: no output" fails spuriously if any existing warning contains "approval".
- **Ruling:** replace the step with `CARGO_INCREMENTAL=0 cargo test -p anima-daemon --no-run 2>&1 | grep -n "approvals/\|approval_state\|agent_runs/approvals\|routes/approvals"`. This reuses the test profile, and building the integration tests also builds the non-test lib, so dead-code warnings show. Match on file paths, not the word.

**I6. A delegated specialist's "Always allow" creates a standing rule the UI can't show or remove.** Plan:9630-9752, Plan:10487-10511, Plan:11551.

- **What's wrong:** The companion's stream carries specialist approvals (inline and on "Waiting for you"). `allow_always` creates the rule on the approval's agent (Plan:3192-3215), but `useApprovals` reads the policy and rules for the companion only. The rule becomes invisible and unrevocable in the console.
- **Why it matters:** a standing allow the owner can't audit.
- **Ruling (cheapest):** `ApprovalCard` takes an `agentId` or `canPersist` prop, and hides `Always allow` when `approval.agentId !== companion.id`. Allow once, Allow for this session (which ends with the session), and Deny stay. Say so in the card: "Rules for other agents are not managed here yet."
- **Alternative:** the Rules section also lists and removes rules of every non-helper agent that has any.

### Minor

- **m1.** Plan:11520 says "Tasks 4 and 5 are independent", but Task 5 needs Task 4's `get_approval`. **Ruling:** strictly sequential 1→14; do not parallelize 4/5.
- **m2. No sweep for orphaned pending approvals.** If the gate future is dropped inside `open_approval`, the approval stays pending with no waiter until restart. This happens when a sibling tool panics in the `join_all` batch, or the task is aborted during `persist.save().await` (Plan:5537-5566); `AbandonGuard` covers only `wait()`. Visual spoofing in the arguments box.** `<pre>{approval.arguments}</pre>` (Plan:9680-9682) is safe from HTML, but bidi and zero-width characters (U+202A–202E, U+2066–2069, U+200B–200F, U+FEFF) pass through `serde_json` unescaped and can make a command look different from what runs. **Ruling:** render those code points as visible `\u{…}` escapes in the card.

- **m6. Stop briefly shows the run as running.** The stop publishes `run.started` for the resume it causes (Plan:6217-6219), just before `run.cancelled`, so the UI flickers to "running". **Ruling:** skip publishing `plan.resumed` in the stop path (the terminal event follows), or keep and accept.
- **m7. Duplicated fixtures and strings.**

## 7. The plan writer's three risks: rulings

**(a) Tasks 5–6 concurrency.**

- **The design is sound.** Every settlement (decision, timeout, stop) takes the control-plane transaction and flips `pending` once under the state write lock (Plan:3096-3098). The loser sees `Resolved`, and replay versus conflict is decided by `was_decided_as`. Wakes and announcements happen under the transaction after the save. The `try_recv` fallback covers a record that was mirrored away.
- **One gap:** an orphaned pending approval (m2).
- **The tests are not deterministic** (I1). Their failure windows need scheduler stalls of about 240 ms, which are realistic under the parallel Nx gate.
- **Ruling:** use patient timeouts, an explicit `settle_approval(TimedOut)` task, and `yield_now()` ordering under the held transaction, with current-thread made explicit. No paused time.

**(b) Self-approval.**

- **How owner auth works:** routes/http.rs:114-150 (loopback Host, no forwarding headers, allowed Origin; else the admin token).
- **Reachability:** the model can reach the owner routes only through an exec call. `web_fetch` refuses loopback (tools/web.rs:98), and bash env is cleared (shell.rs:107). Default `exec: ask` protects until the owner grants a broad exec rule. With one, persistent escalation is real (I2), and git or npm prefixes are equivalent to arbitrary code through default-allowed writes.
- **Ruling:** a documented limit plus UI warnings on broad exec rules. No per-approval token, web-only header, or tool-marker check; all three are forgeable or unreachable. This is proportionate and within §14.

**(c) Behavior change and v7.**

- **Uniform waiting is the spec's intent.** Spec §7.3 names Telegram as the only exception. No rule for unattended sources or job-specific timeout is needed.
- **Documentation is needed** (I3): automations and jobs block their lane for 30 min, Telegram for 15 min, and the CLI gets a 408 at 10 min while the approval lives on.
- **The v7 bump is right.** It follows the M2/M3 precedent and spec §13.3 ("older daemons refuse newer snapshot versions"), and the code paths are correct:
  - `pre_upgrade_backup_path`: <5 → pre-sessions, <6 → pre-live-runs, else pre-approvals.
  - Postgres uses `control_plane.backup.6` through `postgres_backup_key`.
- **Not bumping would also have been fail-safe.** An M3 daemon would drop the rules and policy, which means more asking.
- **What's missing is the rollback bullet** (I4). Also, a future v8 must add its own branch, or `.pre-approvals.bak` would be overwritten.
